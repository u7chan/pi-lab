# Purpose: コンパクション数によるタスク分解のトレーシング

## なぜやるか

pi-issue-pr-workflow（オーケストレーションスキル）で複数PiエージェントがIssue実装〜レビューループを回す際、
「タスク分解（役割・粒度の割り振り）が適切だったか」を後から検証したい。

適切な分解なら各エージェントのコンテキスト圧迫が小さく、粗い分解なら自動コンパクション（文脈を捨てる＝記憶喪失）が増える、
という仮説を、コンパクション数を実測して確かめる。

## 記録したい指標（現案）

- **開発フェーズ**: `impl` の自動コンパクション数 → Draft PR本文に記録
- **レビューループ**: `review` / `pr-fix`(impl) の自動コンパクション数 → PRコメントに記録
- 回数だけでなく `tokensBefore` 合計（＝忘れた文脈量の総和）も取る

## 技術的制約・方針

- **スキルに複雑な指示を入れない**。スキル側はワンライナーの呼び出しだけ、ロジックはシェル/Pythonスクリプト側に寄せる
- シェル優先。可読性が崩れるならPythonも可（本リポジトリではPythonプロトタイプ）
- 自動コンパクションの判別はセッションファイル（JSONL）の `{"type":"compaction"}` エントリを数える方式
  （フックや拡張は使わない。ランタイム変更が不要で、実測が確実なため）
- このワークフローでは誰も `/compact` を手動実行しないため、全コンパクション＝自動とみなせる

## リサーチクエスチョン

1. コンパクション数/`tokensBefore` は「分解の粒度ミス」をどの程度感度よく反映するか
2. モデルのコンテキスト窓・思考レベル・リポジトリ規模の交絡をどう正規化するか
3. 分解診断には何と組み合わせるべきか（Blocker数・修正ラウンド数・検証失敗数など）
4. PR本文/コメントへの記録フォーマットと、マージ後も残るノイズの扱い
5. オーケストレーターが子パネルのセッションファイルを直接読む方式（in-band報告を使わない）は可能か

## スコープ外（今はやらない）

- スキル本体（pi-issue-pr-workflow / herdr / gh / review）の変更
- 実PR・実Issueへの書き込み
- 拡張（extension hook）やRPCによるライブ監視の本格導入
